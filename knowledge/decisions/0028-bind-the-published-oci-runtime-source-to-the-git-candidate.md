# Bind the published OCI runtime source to the Git candidate

Recorded by `agent:claude-opus-5` from the accountable maintainer's exact
disposition. The semantic choice is the maintainer's; this record is faithful
transcription, not a further approval step.

Scope: **Gnostoa-self, first-party OCI runtime source binding only.**

## Context

The published runtime's Gnostoa source was whatever the builder's working
directory happened to contain after `.dockerignore` filtering. Three measured
consequences followed, and they are separable.

**Packaged candidate authority.** Identical Git source produced different
`.gnostoa-source-files` depending on local state; untracked and ignored files
entered it and became live inputs to the project's own candidate text scans; and
even a clean checkout omitted the tracked `.gitignore`. The packaged manifest was
generated by enumerating the copied filesystem, so it inherited whatever arrived.

**Executable source authority at runtime.** A module dropped into `tools/` was
correctly excluded from the manifest and still importable, because the editable
install maps a *directory*: `{'tools': '/opt/gnostoa/tools'}`. Excluding a path
from the manifest does not remove it from the import surface.

**Executable source authority at build time.** An untracked root `pip.py`
shadowed `python -m pip` during the image build and took over the dependency
installation step. It failed loudly under a controlled sentinel; a quieter
variant would not have.

None of this is an exploitability claim. Each required a file in the builder's
own checkout. What fails is the claim that an artifact labelled with a source
revision was built from that revision's source.

The candidate-time measurements live in the
[binding result](../assessments/oci-git-candidate-source-binding-result.md).

## Decision

**A. P2 is required.** The packaged candidate manifest must represent the same
authoritative candidate path set as the checkout, where that set is
`git ls-files --cached --deduplicate`. The invariant is **`S4 == S1`**, absent a
future explicit Decision defining a deterministic packaging exclusion. None exists,
so tracked `.gitignore` and `.dockerignore` both belong in the manifest.

**B. P5 is required.** Repository-derived executable or importable runtime source
must come only from that candidate. Host-local paths outside it must not become
Gnostoa source, and must not influence the Python commands that build the runtime.

**C. P3 is not required.** No general rootfs purity: OS files, installed
dependencies and build-generated metadata stay outside the equality.

**D. P4 is not selected.** `public_surface_digest` remains the public
inheritance identity, not a build-definition identity, and `.dockerignore` is not
added to it.

**E.** Select the **controlled filtered source context**: the runtime build
receives a throwaway context carrying exactly the candidate paths.

**F.** Select **one small self-owned build helper** for the documented runtime
build route. It is build plumbing, not a supported command, not a public CLI
entry point and not adopter guidance.

**G.** Reuse the validated acquisition: a Git-derived NUL-separated manifest, a
bounded named BuildKit context, and a `MANIFEST_SHA256` build argument verified
fail-closed.

**H.** **One** authoritative acquisition drives both the source payload and the
packaged manifest, so they cannot disagree by construction.

**I.** The filtered source uses the **current working-tree contents** of candidate
paths, not committed blobs.

**J.** Therefore deliberate uncommitted edits to tracked files remain buildable.
Development is not silently redefined as committed `HEAD`.

**K.** Ignored and untracked host-local paths do not enter the runtime source
payload.

**L.** `.gitignore` and `.dockerignore` remain candidate source, because they are
tracked candidate paths.

**M.** A `.dockerignore` at the wrapper context root must not filter the
controlled candidate context. This is a measured hazard, not a hypothetical: a
wrapper-root ignore file silently reduced a payload from 214 to 197 paths while
the manifest still claimed 214.

**N.** Source payload and manifest equality is **checked inside the build**,
before any source-sensitive Python installation. A helper that produced a wrong
context must not become authority.

**O.** No secret transport. Secret contents do not participate in build-cache
invalidation, so a secret-mounted manifest can silently serve a stale candidate.

**P.** No full Git history or metadata in the image. **Q.** No network or provider
source authority.

**R.** The **development target keeps the ordinary local build context** and is
**not** covered by this guarantee.

**S.** That development host-context dependence is an **explicit residual by
design**. The same measured `pip.py` shadow still affects a development build.
P5 is selected for the first-party published runtime artifact, and extending it
to the development image would need separate admission.

**T.** No `.dockerignore` remediation. **U.** No `.gitignore` remediation.
**V.** No devcontainer change. **W.** No public-digest correction. **X.** No
CPython work.

**Y.** No new immutable source identity, version, tag or release.
**Z.** OCI publication remains unauthorized and `deployable_artifact` stays
`false`.

**AA.** Issue #7 remains related research only and is not activated. This slice
supplies one concrete narrow result; it takes no authority for workspace
ownership, cleanup ownership, read/write roots, sandboxing or generic hermetic
execution.

## Consequences

- The runtime build now needs the helper. A bare `docker build --target runtime`
  no longer supplies a candidate context and fails closed rather than silently
  falling back to the builder's directory — which is the point, but it does mean
  the documented route is the helper, not raw Docker.
- Four correctness requirements are load-bearing rather than stylistic:
  locale-independent (`LC_ALL=C`) ordering on both sides, a presence guard that
  does not follow symlinks, a wrapper root free of `.dockerignore`, and NUL-safe
  path handling throughout. Each of the first, second and fourth produced a real
  failure during development; the third produced a silent one.
- The Dockerfile gains a stage split. The shared base keeps system state; the two
  branches differ only in where their source comes from. The cost is one
  duplicated install block, accepted so the devcontainer needs no change.
- Only the runtime is bound. The development image remains as trustworthy as the
  checkout it is built from, and this Decision says so rather than implying
  otherwise.
- A plain source archive without Git metadata cannot drive this route, so
  archive-based runtime builds stay outside it.
- Decisions 0022–0027 are unchanged, as are `v0.1.0`, the source-release runbook
  and the prior remediation results. The pip and util-linux clearances stand, and
  the layer-history residual remains governed by Decision 0026.
- The deterministic public-contract-digest defect is untouched and remains the
  expected next disposition.
