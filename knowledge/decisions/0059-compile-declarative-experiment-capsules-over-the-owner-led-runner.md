# Compile declarative Experiment Capsules over the owner-led runner

## Context

Work Item #164 delivered a mechanically qualified execution boundary: OCI isolation,
admitted filesystem and network surfaces, executor lifecycle, coordinator-owned evidence
capture, frozen handoff and deterministic packaging. It deliberately does not own subject
build systems, repository test adapters, hidden-oracle semantics or two-arm orchestration.

Work Item #183 prepared a five-task Phase-D experiment on top of that runner and was frozen
before any executor launch. Its base/reference preflight failed on four of five tasks, and
the four failures were not runner defects. They were preparation defects that only became
visible at execution time, after semantic material had already been frozen:

```text
D0 nextcloud/mail   valid base/reference qualification, reusable
D1 pallets/click    oracle reached click._termui_impl without importing the submodule
D2 pydantic         repository [tool.pytest] addopts injected pytest-benchmark flags
                    that the deliberately minimal image does not provide
D3 pytest-dev/pytest src/_pytest/_version.py is generated by setuptools_scm, is gitignored,
                    and is absent from both frozen trees
D4 pallets/werkzeug an oracle control demanded quoted-realm serialisation that the subject
                    intentionally does not produce, on base and reference alike
```

Each was diagnosed by hand, by reading retained evidence and subject source. Each fix was a
different class: harness preload, test-config isolation, a new runtime identity, and a new
oracle identity. The cost was concentrated in exactly the layer that should have been
reusable, and the diagnosis happened after the failure rather than before the freeze.

Two further properties of that episode shape this decision. First, D1's base result matched
its prospective count `2 FAIL / 0 PASS` while failing for an unrelated import reason: a
count-only comparison would have recorded a false match. Second, the technical failures
created pressure to rewrite already-frozen semantic material, because the frozen packet
bound semantics and execution mechanics at the same moment.

## Alternatives considered

**A. Task-specific preparation scripts and templates.** Keep authoring per-task Dockerfiles,
harness files and shell preparation, with a shared snippet library. This is the status quo
that #183 exercised. It scales linearly in bespoke engineering per task, provides no
mechanical place to detect D3-class preparation requirements or D4-class semantic defects
before execution, and leaves resumability in operator memory and chat history. Rejected.

**B. A declarative spec plus a deterministic compiler and qualifier over #164.** One versioned
experiment specification describes intent; a compiler resolves identities, selects adapters,
derives subject preparation, prequalifies the oracle, qualifies BASE/REFERENCE, consumes
capability certificates and emits content-addressed capsules plus runner profiles. Generated
Dockerfiles, harness files and profiles become compiler outputs. Selected.

**C. A generalised workflow or DAG engine.** Model preparation as arbitrary typed tasks in a
general dependency engine with a plugin ecosystem. This absorbs the whole of #15, introduces
an orchestration framework and a plugin surface, and would have to be qualified as critical
Gnostoa-self infrastructure before it could carry an experiment. It is materially larger than
the problem #187 states. Rejected for v1.

**D. Container-per-task manual preparation with a richer base image.** Push preparation into
fatter images maintained per task family. This does not remove handwritten per-task
Dockerfiles, makes offline determinism harder, and still offers no semantic prequalification.
Rejected.

## Decision

### A. Add a compiler layer, do not modify the runner

A new `tools/capsule` package owns specification parsing, identity resolution, adapter
selection, subject preparation, qualification and freezing. It depends on `tools/experiment`
and never the reverse. It emits runner profiles in the existing
`gnostoa-experiment-runner-profile/v1` shape and reuses `tools/experiment/evidence.py` for
canonical JSON and content addressing rather than introducing a second identity primitive.

The runner's trust boundary is not widened. The compiler may only produce profiles the
runner already validates; anything the runner would reject is a compiler defect, and the
compiler validates its own output with the runner's validator before freezing.

### B. Separate semantic freeze from execution freeze

Two distinct content-addressed freezes.

**Semantic freeze** binds task requirement, failure discriminator, reference provenance
contract, intended oracle roles and controls, and the claim boundary. It is authored, not
inferred, and it is frozen before any qualification runs.

**Execution freeze** binds source, reference, runtime, preparation, harness, oracle, key,
runner, arm and resource identities, and happens only after the selected combination has
actually passed qualification.

A technical qualification failure therefore invalidates execution material and leaves the
semantic record intact. This is the specific defect that made #183 painful: a preparation
defect created pressure to rewrite frozen semantics.

### C. Make preparation an explicit, resumable stage machine

Stages are `DISCOVERED`, `SEMANTIC_FROZEN`, `RUNTIME_PREPARED`, `STATIC_QUALIFIED`,
`BASE_REFERENCE_QUALIFIED`, `BOUNDARY_QUALIFIED`, `EXECUTION_FROZEN`,
`READY_FOR_OWNER_REVIEW`.

Every stage record binds a digest over its complete declared inputs, records whether it was
merely entered or actually completed, and emits a content-addressed receipt on completion. A
stage is reusable only when its recomputed input digest is unchanged **and** its record is
complete, so an interrupted stage can never be mistaken for a qualified one. A changed input
invalidates that stage and its entire downstream closure. State lives in retained files, so
preparation resumes after interruption without reconstructing anything from conversation
history.

Readiness is gated by receipts, not by a flag: `READY_FOR_OWNER_REVIEW` is unreachable unless
every required stage carries a completed receipt, and preflight authority is an object bound to
one exact prepared qualification candidate rather than a truthy value. Naming an experiment is not
enough, because the same experiment identity can be prepared into materially different requests and
run through different backends: a `gnostoa-preflight-authority/v2` record carries the digest of the
experiment, scope, backend and ordered task capsule identities, and the compiler compares it against
the identity it computes itself. That digest is reported by an authority-less prepare, so an owner
approves the exact candidate before any hidden oracle runs, and a candidate that changes afterwards
is refused at the gate.

Materialised subjects are create-only per source identity and their Git tree identity is
independently reconstructed on every run, so retained bytes are verified rather than trusted
because the directory is non-empty.

### D. Keep adapters mechanical and semantics-free

Adapters own invocation mechanics only: module preload, test-configuration isolation,
source-versus-installed subject mode, deterministic generated build artifacts, dependency
mounts and symlinks, and exact argv, cwd and environment. Adapters never contain assertions
about subject behaviour. v1 ships `python-pytest`, `node-vitest` and an explicit
`generic-command` fallback that declares everything rather than inferring it.

Where project metadata can be read mechanically, the inference is recorded with its source.
Where meaning is ambiguous the spec must state it; the compiler does not guess.

### E. Detect subject preparation requirements before qualification, not during it

A subject-preparation contract inspects exact project metadata — for Python the build system,
dynamic version configuration, `setuptools_scm` version files, pytest configuration and
plugin requirements — and classifies the tree as directly runnable or as requiring a named
deterministic preparation.

Preparation names its real producer. The version derivation and version-file generation are a
narrow, versioned Gnostoa algorithm characterised against setuptools_scm 8.1.0, not a wrapper
around that distribution, so the receipt names the Gnostoa algorithm and declares its
compatibility target. Binding an external artifact as the producer would be false provenance
when removing that artifact could not change the produced bytes, and the compiler refuses a
spec that declares one for a scheme that never consumes it.

A required preparation actually runs: it derives its inputs from authoritative Git metadata,
writes the declared artifact, verifies the artifact, and emits a receipt binding the derivation
and the generated digests. The tracked tree must still reconstruct to its declared identity with
the generated paths ignored, so preparation adds and never edits the subject. A required
preparation produces a new prepared-runtime identity; the frozen image identity is unchanged.
Any input that preparation needs must be locally available; in `--offline` mode a missing input
is `BLOCKED` with the exact missing artifact, never an implicit acquisition. Whether the prepared
subject runs end to end is established by BASE/REFERENCE qualification, not asserted by
preparation.

Test-configuration isolation is a provenance-bound projection, not a reset: every declared key is
carried forward except the options attributable to a plugin the runtime does not provide, and the
removed options are inventoried. Warning filters, markers and strictness are never silently
dropped.

### F. Prequalify oracle semantics against declared roles and cited corroboration

Before execution freeze the compiler statically checks the oracle against the semantic freeze:

- every oracle case maps to exactly one declared case, with a declared role of
  `discriminator` or `control`;
- a discriminator must target behaviour the reference actually changes, verified against the
  base-to-reference diff;
- a control must carry a declared corroboration citing where in the frozen base tree its
  expected behaviour is already evidenced, and the compiler verifies that the cited evidence
  exists and matches the control's declared expectation.

Citations are symbol-scoped: the spec names the exact function in the cited file whose behaviour
is the evidence, and only strings inside that symbol can corroborate. A matching value elsewhere
in the same file cannot stand in for the relevant behaviour. A control may instead bind a prior
qualification receipt, which is how an already-valid qualification is reused without a rerun.

An oracle case that asserts behaviour neither changed by the reference nor corroborated in
the subject is `BLOCKED` before execution freeze. This is the D4 class, and it is caught
without executing the oracle and without the compiler judging the behaviour itself: the
burden is an explicit citation, and the check is that the citation is real.

### G0. Keep qualification and experimental execution in separate trust domains

Qualification is coordinator-private and may see the BASE subject, the frozen REFERENCE and
the hidden oracle, because no experimental agent participates. Experimental execution must see
none of them: handing an executor the known-correct reference would invalidate the experiment
outright.

Each task therefore compiles two distinct profiles from two distinct materialisations. The
qualification domain gets one profile per subject over a private copy carrying the oracle. The
execution domain gets its own materialisation of BASE alone, and the compiled execution profile
is checked against an explicit forbidden-surface list -- reference, oracle, identification key,
qualification workspace -- before it is accepted. Generated harness and test-config artifacts
are tagged with the domain that may receive them, so oracle machinery never reaches an executor.

The executor command is declared in the spec and is never inferred from the oracle invocation.
Reusing the harness invocation as an executor command would run the hidden oracle inside the
experimental domain, so the compiler refuses to do it.

### G. Qualify BASE and REFERENCE by cause, never by count

The qualifier records, per case, the observed outcome and the observed failure cause class,
and compares both against the prospective expectation. Collection and import failures are
classified as infrastructure and can never satisfy a prospective `FAIL`. A base case that
fails for a cause unrelated to the declared discriminator is a `wrong-cause` mismatch, not a
match. This is the D1 false-match class.

Hidden oracle execution remains gated by explicit preflight authority and stays inside the
private boundary; no raw oracle or key content enters a public-safe artifact.

Qualification runs through the existing runner rather than a second isolation implementation.
The OCI backend hands the compiled profile and invocation to `tools.experiment` and reads the
evidence the runner retains; the capsule layer contributes no Docker, mount or network logic of
its own.

A qualification result is a typed receipt binding the base tree, reference tree, oracle digest,
runtime image, harness identity and expectation contract. A prior receipt is reused in place of
a fresh run only when every one of those identities still matches and the receipt is qualified;
otherwise the task requalifies or blocks. That is what makes an already-valid qualification
reusable without a rerun.

### H. Make expensive qualifications reusable capability certificates

Runner and backend boundary qualification, relay and network boundary qualification,
sealed-sink qualification and reusable runtime-adapter qualification become content-addressed
certificates binding implementation identity, runtime identity, configuration identity,
certified bounds and evidence identity.

The expected implementation, runtime and configuration identities are declared in the request,
externally to the certificate, and the certificate artifact is itself bound by digest. A
certificate can therefore never self-match the fields it is being checked against. Preparation
consumes a certificate only when those external identities match and the requested bounds fit
inside the certified bounds. Otherwise it requalifies or returns `BLOCKED`. It never widens a
bound to fit.

### I. Keep the public surface small and fail closed

`prepare` performs mechanical preparation and qualification and returns either
`READY_FOR_OWNER_REVIEW` with a complete immutable lock or `BLOCKED` with structured
blockers naming the missing capability or input. The lock is a separate write-once artifact
emitted at execution freeze, binding source, reference, runtime, preparation, harness, oracle,
key, both profiles, executor, reviewer, arm, assignment and resource identities plus every
stage receipt; working state is kept apart from it and is never presented as a lock.

The lock is sufficient to execute without rediscovery. Generated bytes are recoverable from a
content-addressed store the lock references, private material is bound by identity and an
explicit owner-private locator rather than by content, and the source is bound by repository
locator plus tree. `execute` rebuilds the execution capsule from exactly those inputs, re-checks
the execution boundary, and hands the profile to the runner. It performs no discovery and
cannot repair or reinterpret the lock. `status` reports the current stage and
blockers from retained artifacts alone. `execute` consumes a frozen lock under explicit
launch authority and cannot repair, reinterpret or rediscover anything.

### J. Bound the v1 claim

v1 targets the Phase-D task shapes: Python and Node repositories with Git-resolvable bases
and references, executed through the existing runner. It does not claim general language or
build-system coverage, does not claim that a compiled experiment is scientifically valid, and
does not claim completion of #15. It reuses #15-style identity and resume primitives where
they already exist and are suitable.

## Consequences

Experiment preparation becomes declarative and reviewable: the reviewable unit is a spec plus
generated, content-addressed artifacts, instead of a directory of hand-written Dockerfiles
and shell history. The four #183 failure classes each acquire a mechanical detection point
before execution freeze rather than after launch preparation.

The cost is a real new subsystem in a critical path, plus a specification authors must learn.
Spec authoring is deliberately more demanding than the previous ad-hoc path: controls require
cited corroboration, and ambiguity is rejected rather than guessed. That is the intended
trade, because the alternative silently produced an invalid oracle in #183.

Four risks are accepted and bounded. Container image bytes are not reproducible in general, so
equivalence is claimed as exact immutable image identity plus producer provenance, not
byte-identical rebuilds. Semantic prequalification verifies declared corroboration rather than
adjudicating subject behaviour: it catches unsupported assertions, not every wrong one. v1 ships two qualification backends, a
host-local one for pure-Python subjects and an OCI one that reuses the runner; anything else is a
structured blocker rather than a weaker claim. And the execution boundary is enforced over
declared filesystem surfaces, which catches the containment failures this system can create; it
is not a claim about what a hostile process could infer by other means.
